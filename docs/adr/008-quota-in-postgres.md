# ADR-008：配额判定走 PostgreSQL，不走 Redis 计数

日期：2026-08-29（P3.1）
状态：已接受

## 背景

P3 要两类限流：**业务层配额**（花了多少钱、几个研究任务在跑）与
**HTTP 层限流**（每分钟几个请求，P3.2）。两者常被一并塞进 Redis 计数器，
但它们要的东西不同。

## 决策

业务层配额的事实源是 PG：花费明细落 `token_usage` 表，配额判定就是对该表
的一次聚合（滚动 24 小时窗口）+ 一次 `research_tasks` 在跑计数。
Redis 计数只留给 P3.2 的 HTTP 限流。

## 理由

- 配额判定要跟花费记录**同一份数据、同一个事务视角**：Redis 计数器与 PG
  明细是两份状态，任务失败/重试/回滚时必然对不齐，而对不齐的方向恰好是
  「钱花了、计数没加」；
- 配额是低频判定（每次发起研究/追问各一次），聚合走 `(owner_id, created_at)`
  复合索引，代价可忽略；HTTP 限流是每请求判定，那才需要 Redis 的快；
- 滚动 24 小时窗口而非自然日：免时区配置，也免「跨日界刷量」；
- 失败与被取消的任务同样记账——钱已经烧了。不记账的失败路径 = 无限重试
  的免费通道。

## 后果

- 记账写入在图执行**之后**，因此配额是「事后闸」：单次任务可以冲过预算线，
  下一次才被拒。可接受（单次上限由任务本身的轮次/并集帽约束）；要做「事前
  预扣」得先估算 token 数，估算值不能拿去对账，不划算。
- 客户端中途断开的对话轮次目前不记账（生成器被取消，落库那步不执行）——
  与 assistant 消息不落库同源，P3.2「断线续写」一并解决。
- 语料入库的 embedding 花费未计入：LangChain 的 `OpenAIEmbeddings` 丢弃响应
  里的 usage，精确计要绕开封装；相对研究调用是小头，P3 不做。
